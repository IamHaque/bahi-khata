Knowledge Transfer / Onboarding

BahiKhata — a credit-ledger web app for small businesses

Audience: engineers joining the project · Branch feat/v2-multi-business · Version v2 (43/43 stories done) · Generated 16 October 2026 · Single-source review of this repository

BahiKhata replaces a shopkeeper's paper khata (credit notebook) with a customer directory, a per-customer ledger of charges (goods given on credit) and payments (installments received), dashboard roll-ups, CSV import/export, printable statements, and multi-user access with Owner / Editor / Viewer roles. Auth is Google sign-in via Supabase; all data lives in Postgres guarded by row-level security.

1How to use this document

This is a self-contained HTML onboarding document: every fact below was reviewed against the code in this repository (full paths given for verification). Diagrams are rendered with Mermaid.js and load from a CDN — you need internet on first open; a text summary sits next to each diagram.

Suggested 60-minute onboarding path

  1. (5 min) §2 — what the product does and the domain language (charge, payment, void, archive, role).
  2. (10 min) §3–§4 — one architecture diagram, one auth flow, one route map. You now know how the app is wired.
  3. (15 min) §5–§6 — the database: tables, RPCs, RLS. The database is the security boundary; learn it before the UI.
  4. (20 min) §7–§8 — feature deep-dives plus the repo's hard conventions (especially the API-layer rule).
  5. (10 min) §11 — run the setup runbook and get npm run dev working against a scratch Supabase project.

Two warnings that will save you a bad first week

  • Never open the app against a production Supabase project while experimenting. Use a scratch project; the runbook in §11 covers how.
  • The SQL migrations must be applied in a strict order (§11 step 3). The app shows a broken/degraded state if the database is behind the code — that is expected mid-sync, not a bug you introduced.

The one mental model to internalise

The database decides who may touch what; the UI only mirrors it. Every read/write is filtered by Postgres RLS derived from the caller's business_members row (resolved from the browser's JWT — the caller never passes "my user id", and never passes a user id at all for scoped queries). The UI's role matrix hides controls viewers would fail anyway — that is experience design ("viewers never see a control that would fail"), not security.

3.2 System context (words)

There is no custom backend server: the SPA talks directly to two Supabase surfaces — GoTrue (supabase.auth.*: session, Google OAuth, sign-out) and PostgREST (supabase.from(...) for tables/views, supabase.rpc(...) for functions). Security is declarative: Postgres RLS policies + security-definer RPCs check the caller's identity via auth.uid()/JWT. The app authorizes requests only by asking Postgres; there are no server-side endpoints to lock down beyond the policies (§5).

3.3 Auth & boot flow

Text: AuthProvider restores the session (getSession + onAuthStateChange); sign-in is Google OAuth with redirectTo: window.location.origin + "/". Signed-out visitors are bounced to /login by ProtectedRoute (the deep link is remembered in the from state and restored after consent). While the memberships query loads, signed-in users see one BusinessBootSkeleton. The LandingResolver at / then routes: own business → that business's dashboard; member/invited elsewhere → /businesses; nothing at all → /onboarding/business.

A Google sign-up also creates the user's profiles row via the handle_new_user trigger on auth.users (migration 0001) — that profile is what members lists, "Recorded by" names and avatars read.

3.4 Mutation data flow (the "how does a write actually work" path)

Every write in the app follows the same five hops. Learn this once and every feature behaves the same way.

Lost-access wiring (S-27): a global QueryCache/MutationCache onError in src/lib/queryClient.ts refetches businessKeys.memberships() whenever any query or mutation fails with forbidden (excluding the memberships query itself). The BusinessGuard (§4) then notices the vanished membership and routes the user out with "You no longer have access …" — or "This business no longer exists" if the business_exists probe (RPC, migration 0003b) says the row is gone. Defaults: retry: false, staleTime: 0, refetchOnWindowFocus: false.

The BusinessGuard (S-17, S-27) — worth reading in full

src/features/business/components/BusinessGuard.tsx wraps the whole /b/:businessId tree. The businessId must be one of the user's memberships; blocked children never mount, so no data call is ever made for a business the user cannot see. Crucially it distinguishes two vanishings:

  • Removed by the owner → toast "You no longer have access to <name>" → to /businesses.
  • Business deleted → toast "This business no longer exists" → to the landing resolver. Only the business_exists(uuid) security-definer RPC can tell these apart (RLS makes them identical); it deliberately exposes nothing else.

5Database reference

5.1 Entity–relationship diagram

Enums (created idempotently)

  • transaction_type: charge, payment
  • transaction_status: active, edited, voided (see §8.5 lifecycle)
  • transaction_source: manual, import
  • business_role: owner, editor, viewer
  • invitation_status: pending, accepted, declined, revoked

5.2 Key integrity rules worth remembering

  • One owned business per user: unique index businesses_one_per_owner(owner_id) + a check inside create_business.
  • One owner row per business: partial unique index on business_members(business_id) WHERE role='owner'; owner rows never change or get removed except by deleting the business.
  • Tenant match trigger: transactions_business_match refuses a transaction whose business_id differs from its customer's (SQLSTATE 23503).
  • Invitation hygiene: emails stored lowercased (CHECK email = lower(email)); invites only ever offered as editor|viewer; one pending invitation per business+email (client surfaces error 23505 as "An invitation is already pending for this email.").
  • Never hard-delete transactions: there is deliberately NO delete policy on transactions. Rows are voided (§8.5) and remain as history. Customers are the only thing that can truly vanish, and only via the owner-only RPC below.

5.3 RPC catalog (functions the client calls)

security definer functions run as the DB owner and must do their own authorization (they do — every one validates via is_member/has_role or the JWT email); security invoker functions run with the caller's rights, so the same RLS that governs table reads scopes them automatically.

5.4 The one view: customer_balances

create view customer_balances with (security_invoker = true):

balance per customer = sum(charge ? +amount : −amount)
                       filtered WHERE status IN ('active','edited')
included: every non-deleted customer (archived ones too — the Archived filter needs them)

It is the single source of every balance the UI shows — list rows, ledger hero, picker previews, totals. The old v1 security-definer balance RPCs were dropped by migration 0003 precisely because they ignored tenancy (they bypassed RLS). The transactions list additionally embeds it as customer_balances!inner(balance).

7Feature deep-dives

7.1 Auth & session (src/features/auth/, src/contexts/AuthContext.tsx)

  • Google OAuth only; flow started by signInWithGoogle() with redirectTo: window.location.origin + "/" — consent returns through Supabase to the app root, where the landing resolver decides.
  • AuthProvider exposes { session, user, loading, signInWithGoogle, signOut }.
  • Sign-out clears the entire TanStack cache (queryClient.clear() in BusinessProvider) so nothing from the previous session survives.
  • ProtectedRoute (src/components/) guards everything else; the attempted deep link is restored after sign-in.

7.2 Business lifecycle (src/features/business/)

  • Boot: BusinessProvider loads useMemberships → one getMemberships() read joins business_members → businesses (with owner profile name) and my pending invitations, all RLS-derived. Result statuses: loading | ready | none | forbidden; a loading signed-in user renders BusinessBootSkeleton exactly once.
  • Create: createBusiness RPC; the DB enforces one owned business per user and auto-adds the owner membership (trigger).
  • My businesses page: own business, shared-with-me businesses (role + owner name), invitations with accept/decline; sidebar BusinessSwitcher (own first, shared, All businesses, Create business when I own none — keyboard + aria-checked).
  • Settings: owner edits details (zod-validated form); non-owners see read-only details. Backup section (everyone). DangerZone (owner): typed-exact-name delete dialog — with a "Keep a copy first" backup link — showing counts of customers/transactions/members/invitations gathered by getBusinessImpact; cascade FKs make the DB delete atomic.
  • Lost access: described in §4.

7.3 Customers (src/features/customers/)

  • List (server-side, S-28): a single PostgREST query in queryCustomers — ilike search over name/phone (wildcards escaped; punctuation blanked so "(0171)" still matches), balance status filter (owes / credit / settled / archived — archived is the one view that includes archived rows, with real balances), sort via customer_balances.balance/name/created, paging with exact counts, embedded last activity, plus an unfiltered count for the summary strip. Page state lives in the URL (q, status, sort, dir, page) and survives reload/back-button.
  • Form (S-29): CustomerFormDialog on the shared form kit; zod schema in schemas.ts (name 1–100, phone/email plausibility, tag limits); name-first layout with "Additional details" disclosure; duplicate name+phone hint with an "Open existing customer" link; success toast offers "Add transaction".
  • Archiving (S-30): setCustomerArchived stamps archived_at; archived customers step out of lists, search, pickers and totals (but keep history on their own detail page); Undo toast for 8 s; the Archived status filter is how you find + Restore them.
  • Permanent delete: the owner-only atomic RPC (§5.3); confirm requires typing the exact name; the dialog first states the exact transaction count that will go.
  • Detail page (S-31): header (avatar, tags, tel:/mailto: contacts, address, Edit, actions menu), balance hero with BalanceBadge + Total charged/Paid/Last activity stats, Add charge/Add payment buttons that preset the entity sheet's type, and the ledger from customer_ledger: Date / Type / Note / Amount / Balance after, newest first, All/Charges/Payments filter, Show-voided toggle (on by default), mobile card layout, archived banner with Restore, empty/error states. Statement opens the printable page (§7.7).

7.4 Transactions (src/features/transactions/)

  • One shared sheet (S-32/33): TransactionSheet handles both add and edit. Because it's opened programmatically from anywhere (topbar, row menus, ledger, dashboard buttons, even a toast-inside-a-dialog that is unrelated to the Topbar's tree), it's exposed through a tiny module store (sheetStore.ts, useSyncExternalStore): openTransactionSheet(customer?, presetType?), openTransactionEdit(tx, customer), plus focus-return-to-trigger tracking. Exactly one instance is mounted (in the Topbar).
  • Add mode: Charge/Payment segmented control, searchable customer picker (template dropdown + inline "Add ... as a new customer"), live current → resulting balance preview off the customer_balances view, inline validation (amount > 0, ≤2dp, no future dates, ≤500-char note), failure keeps your input, viewers see no add actions anywhere.
  • Edit mode: same sheet, customer shown not picked, preview recomputes honestly (removes the old entry's effect first), saves with status='edited' + updated_by/at stamps; a voided row can't be edited (.neq('status','voided')); provenance (source/created_by/customer) is never editable.
  • Ledger badges: rows keep an EditedBadge ("Edited by <name> on …"; creator/editor who left → "Former member"), and voided rows stay visible, muted and struck-through with a Voided badge.
  • Void & restore (S-34): VoidTransactionDialog ("Void this payment of ₹500?" + optional ≤200-char reason, verb-exact Void transaction button); toast offers Undo for 8 s; Restore goes through the server-side RPC so the row decides its own restored status (§5.3). Balance + all totals exclude voided rows (they always did server-side; the UI now proves it).
  • Transactions page (S-35): detailed view (Date, linked Customer, Type, Note, Amount, Recorded by, status/source badges) with server-side filters — date presets (Today/This week/This month/Last 30 days/Custom; default This month), type pills, customer picker, debounced text search over customer name/phone/note, Include-voided — every filter in the URL as removable chips. Summarized view groups by day/week/month through transaction_rollup. The totals footer shows Charges/Payments/Net for the whole filter (the ungrouped rollup row), independent of paging.

7.5 Dashboard (src/features/dashboard/)

  • KPIs (S-36): four StatCards from dashboard_summary — "Total owes you" is the headline receivable, plus "Total you owe", "Open accounts", "Today's activity" (count + net). The figures are server-computed: voided excluded, archived customers excluded.
  • Top outstanding (≤8, avatar + link; "All settled" when empty) and a Today card that links to ?range=today — the transactions page footer shows the identical count/net (one timezone caveat, DEV-14 / backlog B-09).
  • Trends (S-37): TrendChart (recharts, tokens --chart-1/2) from daily_activity, 7/30/90 selector; a visible text summary + an sr-only data table equivalents (zero days are rows, not gaps).
  • Activity feed: last 10 entries as full sentences with links; voided rows and archived customers never appear; departed creators degrade to "Former member".
  • First-run card lists: add first customer → record first transaction → invite a teammate (Owner-only step). Quick actions are Owner/Editor-only; every section has its own skeleton/error/retry.

7.6 Members & invitations (src/features/members/)

  • Members page (S-22): all members with role badges (owner-first); owners see the Invite dialog + a pending-invitations section; editors/viewers see a Leave business button, owners see the note "Owners cannot leave. Delete the business instead."
  • Invite (S-23): email lowercased + validated (zod), role Editor/Viewer (default Viewer), inline rejections (your own email, existing member, already-invited) with the DB's unique-pending index as backstop (error 23505 mapped). "Copy app link" for the invitee.
  • Manage (S-25): row actions — change role / remove — via the change/remove RPCs with named confirmations. Only the membership row goes: the person's transactions stay, their name resolves to Former member once their profile is unreachable (SQL test 0002c pins this data contract — the UI degrade is by design, not a bug).
  • Being invited (S-24): invitation count badge in the top bar; accept/decline from /businesses; a stale/revoked invitation surfaces "This invitation is no longer available." and the card disappears.

7.7 Import, export, backup, statement (src/features/import-export/)

CSV import (S-38) — flow below; the parser in src/lib/csv-import.ts is shared legacy code (kept, well-tested), the new import-export feature owns the page and the atomic RPC.

Exports & backup (S-39): every member, including Viewers, may export. Customers/Transactions lists get "Export CSV" buttons that re-run the page's current filters with 500-row server-side paging (progress in the button: "Exporting… done/total"); Settings + the delete dialog offer a whole-business backup (customers.csv then transactions.csv). Printable statement: /b/:bid/customers/:cid/statement — business + customer header, From/To period selector, every entry with the server's own balance_after, recomputed closing balance; print stylesheet hides the shell (print:hidden on sidebar/topbar, white-paper body rule) — no new dependencies.

8Shared patterns & conventions (the repo's laws)

8.1 The API-layer rule — features/*/api.ts is the ONLY Supabase caller

  • The module src/lib/supabase.ts holds the single createClient (URL + anon key from VITE_* env vars).
  • Only src/features/*/api.ts files may import it. src/lib/__tests__/clientHygiene.test.tsx scans imports and createClient occurrences and fails the build on any violation.
  • Each api.ts wraps its reads/writes in guard() → toAppError; each domain's hooks.ts builds TanStack queries/mutations on top, calling assertCan in every write's mutationFn.

8.2 Error model — src/lib/AppError.ts

AppError carries one of four codes — forbidden | network | validation | unknown. toAppError normalizes everything: TypeError → network; SQLSTATE 42501 / "row-level security" → forbidden; 23505 → duplicate validation; 23503 → dangling-reference validation; 22xxx/23xxx → validation; PGRST* → unknown with retry. Every mutation failure surfaces as a toast that says what failed and what to do ("Could not archive customer. Try again."); successes are past tense ("Customer archived.").

8.3 Query keys & caching — src/lib/queryKeys.ts

Every key is business-scoped: ["business", businessId, ...] (the scope() helper). That prefix is load-bearing: losing access purges the business with one removeQueries, and deleting the business drops all of its caches at once. User-level keys (memberships, myInvitations, businessDetail, businessImpact) sit outside the prefix. Hygiene tests keep the key catalog in sync with real usage. Compartmental note: pagedList and plain list are deliberately separate keys (different query shapes must never share a cache entry).

8.4 UI system

  • Forms: EntityDialog — the same component for create and edit, dialog (desktop) / bottom-sheet (side="bottom") modes; zod schema + shared field components in components/app/fields/; inline errors, spinner on submit, keep inputs on failure.
  • Destructive confirms: ConfirmDialog with a specific verb ("Archive customer", "Void transaction"); irreversible ones require typing the exact name.
  • Lists: column-driven DataTable with the five states (loading / empty / no-results / error / data), server-side sort + paging, aria-sort, "Showing N of M" live region, sorted-column announcements, card mode under 768px, embedded RowActionsMenu; list state in the URL.

  • Theme: custom ThemeContext light/dark/system, OKLCH semantic tokens, WCAG AA verified both themes by scripts/contrast-audit.cjs; prefers-reduced-motion collapses transitions.

10Security model

Condensed from docs/SECURITY.md — read that file for the full threat→control→proof table. The highlights a new engineer must know:

  • Tenancy: every table is RLS-filtered by membership resolved from the JWT; an outsider's reads return zero rows and writes are refused. Cross-tenant RPC abuse is refused by membership checks inside the functions.
  • Roles: Viewer writes are refused at policy level, not merely hidden. Editor escalation (permanent delete, role change, member removal, business delete) → owner-only RPCs/policies with 42501.
  • Invitations: only the matching JWT email can respond, once; owners can't leave their own business.
  • Secrets: only the anon/publishable key ever ships. clientHygiene.test.tsx fails the build if a service-role key appears anywhere in the repo or bundle (run npm run build first to include the bundle scan), and pins the exact shape of .env.example / .env.
  • Input safety: React escaping everywhere (HTML-sink scan + rendered-payload proof); exported CSVs are formula-neutralized (= + - @ → prefixed).
  • Auth deep links: protected routes remember the destination and resume after sign-in.

  • v1 (master @ cc92edb): single-business, hand-rolled data layer, wide-open RLS ("every authenticated user sees everything"), no routing/paths discipline, no CI. Baseline audit in docs/ARCHITECTURE-BASELINE.md.

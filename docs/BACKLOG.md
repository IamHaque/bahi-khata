# Backlog (ideas beyond the PRD)

Extra ideas surfaced while executing stories. Not commitments — candidates
for a later hardening/polish story or a post-v2 pass.

| # | Idea | Where it came from | Notes |
| --- | --- | --- | --- |
| B-01 | Grouped "last activity" instead of embedding every transaction per customer row | S-28 `queryCustomers` embeds `transactions(occurred_at)` (ungrouped) so each list row carries its history's dates | Payload grows with transaction count per page of rows. After S-20's contract phase a `customer_last_activity` view (or lateral join in the query) caps it at one row per customer; the client's `last_activity` field is already the contract to keep. |
| B-02 | DataTable loading headers keep the sort affordance | S-28 tests: the loading branch renders plain `<th>`s (no `role`/`aria-sort`/cursor) while data rows are skeletons | Harmless for one fetch, noticeable on slow links: headers look dead until data lands. A `sortable` pass-through on the skeleton header would keep the table's affordance stable across all five states. |
| B-03 | Rows-per-page in the URL | S-28 keeps `pageSize` in component state (PRD lists only `q, status, sort, page` for the URL) | Reload resets to 10; sharing a "same view" link at 25 rows/page would not restore the size. Trivial to add if anyone asks for shareable page sizes. |
| B-04 | Re-point the "Customer added" toast action at the transaction sheet | S-29 — the toast action promised "Add transaction" before S-32 existed, so it opens the new customer's ledger for now | When S-32's TransactionSheet lands, decide whether the toast action should open it with the new customer preselected (touches S-29's dialog, outside S-32's touch zone — needs the same documented-stretch treatment). Until then the action is honest: it goes where the customer's transactions live. |
| B-05 | "No customers yet" when every customer is archived | S-30 — with status=all and zero active customers but archived ones existing, the empty state invites "Add your first customer", which is the right next action but reads oddly for a business with history | One extra count (archived-inclusive) or an all-archived probe would let the copy say "All customers are archived" with a jump to the Archived filter. Pure copy polish; nothing breaks today. |
| B-06 | Decide whether "Today activity" excludes archived customers | S-30 — deliberately transaction-derived: txns recorded before an archive still happened, so count/net stay honest even for a customer archived the same day; `dashboard_summary`'s customer-derived totals DO exclude archived (migration 0004) | When S-36 revisits the dashboard, decide whether the Today widget should match `dashboard_summary`'s exclusion or keep its ledger-history stance — today the two can disagree in the narrow "archived after recording today's txn" case. |

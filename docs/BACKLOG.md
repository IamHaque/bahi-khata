# Backlog (ideas beyond the PRD)

Extra ideas surfaced while executing stories (v2 and v3.1). Not
commitments — candidates for a later hardening/polish story or a
post-v3.1 pass. B-01, B-04, B-06 and B-09 are done and kept as history.

| # | Idea | Where it came from | Notes |
| --- | --- | --- | --- |
| B-01 | Grouped "last activity" instead of embedding every transaction per customer row | S-28 `queryCustomers` embeds `transactions(occurred_at)` (ungrouped) so each list row carries its history's dates | **Done by S-53 + the v3.1 migration:** `customer_balances` now computes `last_activity_at` (and `last_payment_at`); the list reads the view column and the transactions join is gone. Kept as history. |
| B-02 | DataTable loading headers keep the sort affordance | S-28 tests: the loading branch renders plain `<th>`s (no `role`/`aria-sort`/cursor) while data rows are skeletons | Harmless for one fetch, noticeable on slow links: headers look dead until data lands. A `sortable` pass-through on the skeleton header would keep the table's affordance stable across all five states. |
| B-03 | Rows-per-page in the URL | S-28 keeps `pageSize` in component state (PRD lists only `q, status, sort, page` for the URL) | Reload resets to 10; sharing a "same view" link at 25 rows/page would not restore the size. Trivial to add if anyone asks for shareable page sizes. |
| B-04 | Re-point the "Customer added" toast action at the transaction sheet | S-29 — the toast action promised "Add transaction" before S-32 existed, so it opened the new customer's ledger for now | **Resolved by S-32:** the action now calls `openTransactionSheet()` with the new customer preselected (documented stretch on S-29's dialog — the same treatment the row predicted). Kept in the table as history. |
| B-05 | "No customers yet" when every customer is archived | S-30 — with status=all and zero active customers but archived ones existing, the empty state invites "Add your first customer", which is the right next action but reads oddly for a business with history | One extra count (archived-inclusive) or an all-archived probe would let the copy say "All customers are archived" with a jump to the Archived filter. Pure copy polish; nothing breaks today. |
| B-06 | Decide whether "Today activity" excludes archived customers | S-30 — deliberately transaction-derived: txns recorded before an archive still happened, so count/net stay honest even for a customer archived the same day; `dashboard_summary`'s customer-derived totals DO exclude archived (migration 0004) | **Decided by S-36:** the dashboard's Today figure now comes from `dashboard_summary` itself, so the page is consistent everywhere — archived customers are excluded from the Today count/net exactly as from the KPI totals (their history stays visible on their own detail page and on the transactions page only until archived — S-30's rule). The ledger-history stance left with the v1 widget. |
| B-07 | Auto-select a customer created inline from the sheet's picker | S-32 — "Add … as a new customer" inside the picker creates the customer and refreshes the list, but the user must still click them in the picker (same as v1 quick add) | The v2 dialog doesn't return the created row to its caller; an `onCreated` callback (or the sheet's own store message) could preselect them and skip one click. |
| B-08 | Full revision history for transactions | S-33's Done-when explicitly defers it: only the LAST editor and the moment of the last edit survive (`updated_by`/`updated_at` are single columns; the audit trail lives in Supabase's `auth.logs`, not the app) | A `transaction_revisions` table (append-only, written by the same update path or a trigger) would let the Edited badge open "changed 500 → 450 by Eli on …, by Asha on …" history. Needs a migration + an RLS design; until then the badge's single sentence is all the PRD requires. |
| B-09 | `p_timezone` overload of `dashboard_summary` | DEV-14 — the RPC cuts "today" in the DB session timezone (UTC) while the S-35 page cuts the browser's local day, so entries recorded in the local 00:00–06:00 window are counted by the transactions page but not by the dashboard's today KPI (for a UTC+6 user) | **Done by the v3 migration (S-50) + S-52:** `dashboard_summary(uuid, text)` carries `p_timezone` **with a `default 'UTC'`** — the uuid-only overload is dropped but a one-argument call still resolves (the migration says so explicitly), so the old client keeps working with the old UTC behaviour. The new client always sends the browser's IANA zone (shared `currentTimeZone()` helper, UTC fallback). Note V-07d called the parameter "mandatory"; the default makes it optional at the SQL level (S-67 correction). Kept as history. |
| B-10 | Exempt purely-numeric cells from the safe-CSV prefix | S-39 - the PRD's safe-CSV rule prefixes ANY cell beginning with -, so a plain negative amount exports as text (shown as apostrophe + -500) and stops summing in spreadsheets | Correct as pinned (a leading - can start a formula, e.g. -2+3+cmd), but exports of balances/amounts stay numeric only if the escape skips strings that are entirely an optional minus and digits. One regex branch in escapeCsvCell, plus a re-read of the S-39 safe-CSV test. |
| B-11 | Direction words on the mobile customer card | L-08 - the mobile LeaderRow card shows the balance in tone colour only (spec: leading/label/sub/amount), while the desktop cell adds "owes you" / "you owe" beneath | A screen-reader user on mobile hears just the amount, and colour alone carries receivable-vs-credit (WCAG 1.4.1, not an axe rule). Fix candidates: fold the words into the card's sub-line or extend LeaderRow with an amount-sub slot. |
| B-12 | Automatic purge or export of the deletion log | v3.1 PRD 2.2 / Q-6 — the log grows forever (kept until the business is deleted, D-18) | A purge tool (age or count cap, Owner-only, itself logged) or a log export (CSV/JSON) would keep large ledgers tidy. Additive migration + one RPC. |
